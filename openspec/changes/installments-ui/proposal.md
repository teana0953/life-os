# 定期扣款的前端

## Why

後端已經上了(life-os-backend#82),而**使用者完全看不到這個功能** —— 沒有任何建立入口,分期產生的交易在明細裡跟普通交易長得一樣。

## What Changes

- **獨立的「定期扣款」建立入口**,兩種模式:總額平均分(信用卡分期)、每期固定(房貸、綁約訂閱)。
- **明細裡的分期交易顯示「第 N 期 / 共 M 期」**,並給一個到那組計畫的出口。
- **計畫頁**:看整組、改整組、一次清償。清償的金額**只有總額模式系統算得出來**,每期固定模式要使用者從銀行抄 —— 所以清償 UI 必須先看 `mode`。

## 定位:講「定期扣款」,不只講分期

同一個機制吃下三種:信用卡分期(總額÷期數)、綁約 N 個月的訂閱、房貸車貸(每期金額×期數)。

**要填期數,所以沒有期限的訂閱(Netflix 那種一直扣到取消)還不支援** —— 那需要排程 tick,是獨立的 feature。文案要說出來,否則使用者會拿它記 Netflix 然後得到一個 12 期就停掉的假訂閱。

## 為後續的分帳分期讓路

**分帳分期(對方每月還你)是已知的下一步**,而它會讓一筆交易**同時**是分帳鏡像和分期的第 N 期 —— `split_expense_id` 與 `plan_id` 是兩個獨立的可空欄位,沒有任何約束禁止並存。

現有的 sheet 用 `_isMirror` 做二選一的分支。這個 change **不假設兩者互斥**:分支寫成明確的優先序,計畫層級的動作(管理、清償)以「這個 plan 是不是我的」為條件,而不是「這是不是分期」。

**現在就為「兩者皆非 null」寫測試**,即使目前的後端產不出這種資料 —— fixture 手動建得出來。不寫的話,分帳分期那輪會發現前端的判斷從根上就錯了,而不是漏了一個 case。

## Impact

- `FinanceTransaction` 加 `planId` / `installmentNo`;新的 `InstallmentPlan` 模型與 repository 方法(4 個端點)。
- 明細列與編輯 sheet 都要改,而 sheet 已經有分帳鏡像的分支。
- **建立分期不會發任何預算警示**(後端裁定),UI 不要暗示會提醒。
- **淨值不會因為分期變動**,360 期的房貸不會自動把貸款餘額減下去 —— 要讓使用者知道,否則他會等它自己更新。
- **非 TWD 的分期不會出現在預算進度裡**。

## 明確不做

- **沒有期限的訂閱**(需要後端排程 tick)。
- **分帳分期**(對方每月還你)—— 那會推翻 `finance-ledger` 現行的「還錢不是花錢、結清不產生鏡像」,並改變餘額語意,是獨立的 backend change。
