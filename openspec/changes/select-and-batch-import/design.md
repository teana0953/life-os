# chaodays 匯入：可選類型 + 長區間自動分批（issue #86）

## 問題

issue #86：「可以選擇要匯入哪些資料 —— 匯入太長的時間區間，會被對方的 server 擋住」。

現況（`ChaodaysImportController.import`）：五種類型（體重／飲食／飲水／排便／飲食目標）**固定全跑**、順序寫死，每個類型對整段 `[startDate, endDate]` 打**一個** request（後端 `http-chaodays-client.ts` 直接把 `start_date`/`end_date` 放進 chaodays 的 query）。第一個失敗就停，整體轉 `unavailable`。

因此使用者要匯一段長區間時：

- 沒辦法只補匯某一種（例如只想重補飲食），一定得五種全跑；
- 區間一長，chaodays 就擋下來，而且沒有任何降級 —— 整批失敗。

## 設計決策

### D1 — 長區間自動切成半年一批，依序送

前端把 `[start, end]` 切成每批最多 **183 天**，對每個選中的類型依序跑完它的所有批次。

**批次大小 183 天（固定天數），不是月曆上的 6 個月**：月曆加法有月底空洞（8/31 + 6 個月沒有 2/31，會跳成 3/2 或 3/3），切點會隨起始日不同而漂移、也難測。固定天數的切點完全可預測。

183 天這個值是**使用者依實際經驗指定**的，不是量測出來的上限。若之後仍被擋，改小這個常數即可 —— 它是單一具名常數，不散落在各處。

**切在前端而不是後端**：後端跑在 Cloudflare Workers，單一 request 有 subrequest 與時間上限，把 N 批塞進一次呼叫等於把長區間的風險換成 Worker 逾時的風險。前端切則是每批一次獨立的後端呼叫，各自完整，而且進度可以逐批回報。**後端完全不動。**

### D2 — 類型可選，至少選一個

五個類型各自可勾選，預設**全選**（維持現有行為，老使用者不會突然發現東西沒匯到）。全部取消勾選時送出按鈕停用 —— 沒有「匯入零種資料」這種有意義的操作。

選擇 UI 直接放在既有的結果列 `_TypeResultRow` 上，而不是另外開一張「選擇類型」卡片：同一份類型清單既是選擇項也是進度顯示，使用者勾了什麼、接下來就在同一列看到它跑起來。多開一張卡片會讓畫面出現兩份相同的類型清單。

未選的類型在匯入期間維持 `notAttempted`（灰色圈），與「跑到一半被 auth 失敗中斷、還沒輪到」的呈現一致 —— 兩者對使用者的意義相同：這次沒有動它。

### D3 — 進度與結果以「類型」為單位，批次是次要資訊

執行順序是 **type-major**：選中的類型依序跑，每個類型跑完自己的全部批次才換下一個。理由是既有 UI 就是一列一個類型，type-major 讓「這一列跑完了」等於「這個類型完成了」，不需要重畫進度模型。

每個類型在匯入中額外顯示 `第 n／共 m 批`；批次數為 1 時不顯示（絕大多數短區間匯入不該因為這個功能變吵）。

### D4 — 一個類型的多批結果合併成一筆 summary

`ChaodaysImportSummary` 的 `imported` / `skipped` 直接相加。`glucoseImported` 與 `waterTargetsImported` 是可空欄位（只有 diet／dietTarget 會給），合併規則：**只要任一批非 null 就相加，全部為 null 才維持 null** —— 否則某一批剛好沒有血糖資料時，整個類型的血糖數字會被抹成 null。

使用者看到的仍是一個類型一行結果，不會因為分批而變成三行。

### D5 — 失敗語意維持現況：停在第一個失敗

某一批失敗時，該類型標記 `failed`、整體轉對應狀態（`authFailed`／`needsReauth`／`unavailable`），**不繼續跑後面的批次或類型**。這是現行語意，本 change 不改。

已經成功寫入的批次**保留**（不回滾）——匯入本來就是逐日 upsert、可重跑，且 `DataRevision` 的既有規則是「至少一批成功就 bump」。使用者重跑時已匯入的日子會落在 `skipped`。

### D6 — 憑證仍然只在呼叫期間存在

分批不改變憑證的處理：`chaodaysUid`／`chaodaysPassword` 仍然是每次 use case 呼叫的參數，controller 不持有、不儲存。批次迴圈只是多呼叫幾次同一個 use case。

## 元件

| 檔案 | 改動 |
| --- | --- |
| `lib/contexts/import/domain/date_range_batches.dart`（新） | 純函式：把 `[start, end]` 切成每批最多 N 天的區間清單 |
| `lib/contexts/import/domain/chaodays_import_summary.dart` | 加合併（多批 → 一筆），含可空欄位規則 |
| `ChaodaysImportController` | `import` 接受選中的類型集合；對每個類型跑批次迴圈；`TypeState` 帶批次進度 |
| `ChaodaysImportScreen` | `_TypeResultRow` 加勾選；`_canSubmit` 要求至少一種；匯入中顯示批次進度 |
| l10n ARB ×3 | 批次進度文案 |

切分與合併都是**純函式**，放在 domain、單元測試直接覆蓋；controller 只負責編排。後端與 `ImportRepository` 介面不動。

## UI/UX 設計

### 使用者路徑

**主路徑**：進匯入頁 → 填帳密、選日期區間 → 五個類型預設全勾，可取消不需要的 → 送出 → 每個選中的類型依序跑，長區間的類型顯示 `第 n／共 m 批` → 全部完成顯示完成訊息與各類型結果。

**補匯單一類型**：只勾「飲食」→ 其餘四列維持灰色未動 → 只有飲食那列跑。

**例外路徑**：
- 全部取消勾選 → 送出按鈕停用（不是按了才報錯）。
- 某批失敗 → 該類型顯示失敗、整體顯示既有錯誤訊息；已匯入的批次保留，重跑時會落在 skipped。
- 憑證錯誤 → 維持現況：該類型退回未嘗試、整體顯示帳密錯誤。

### 介面與一致性

不新增畫面。勾選框加在既有結果列的最前面，取代匯入前的灰色圈圖示；一旦開始匯入，該位置換回狀態圖示（進行中／成功／失敗），所以同一個位置在「選擇階段」和「執行階段」各有明確且不重疊的意義。匯入進行中所有勾選框停用，與畫面上其他輸入（帳密、日期）在 `_isImporting` 時的處理一致。

### 狀態設計

- **未選取**：灰色未勾，整列文字維持一般色（不是 disabled 的灰），因為它隨時可以被勾選。
- **匯入中（單批）**：維持現況的轉圈 + 類型名稱。
- **匯入中（多批）**：轉圈 + 類型名稱 + `第 n／共 m 批`。批次數為 1 時不顯示這段。
- **完成／失敗**：與現況相同，一個類型一行結果（多批已合併）。

### 可及性/理解性

勾選框是標準 `Checkbox`，有既有主題樣式與點擊區域。批次進度是純資訊，不需要使用者理解「為什麼要分批」——它只是告訴使用者「還在跑、跑到哪」，避免長區間匯入時看起來像卡住。

## 測試策略

- **切分純函式**（單元）：單日區間 → 一批；剛好 183 天 → 一批；184 天 → 兩批且不重疊不遺漏；跨年；start == end。
- **summary 合併**（單元）：相加；全 null 維持 null；部分 null 只加非 null 的。
- **controller**（單元）：只選一種時其他類型不被呼叫且維持 notAttempted；長區間對同一類型呼叫多次且參數是連續不重疊的子區間；多批結果合併成一筆；某批失敗即停（後續批次與類型都不再呼叫）；至少一批成功仍 bump `DataRevision`。
- **screen**（widget）：預設全勾；取消全部後送出停用；只勾一種時只送那一種；匯入中勾選框停用；多批時顯示批次進度、單批時不顯示。
- **既有測試不得退化**：現有 import controller/screen 測試在「全選」語意下應維持通過。

## 不做（YAGNI）

- 批次失敗自動重試／跳過續跑 —— 分批本身就是為了不被擋，先觀察實際效果再決定是否需要。
- 批次大小做成使用者可調 —— 使用者指定半年就是半年，多一個設定項只是把選擇困難丟回去。
- 後端分批 —— D1 已說明為何切在前端。
- 記住上次勾選的類型 —— 預設全選已涵蓋主要情境，記憶狀態要處理「新增類型時預設值」等額外問題。
