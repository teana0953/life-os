# 設計:空狀態的兩層標準

## 問題

**至少 20 個**空狀態,**五種**形狀(第五種是 `care_today_summary_card` 的 InkWell **Row** 橫幅),標題樣式五種做法(titleLarge / titleMedium / bodyLarge / bodyMedium / 預設),間距三種(8 / 12 / 16),icon 兩種尺寸(48 / 40),多處沒套淡色。

第一版盤點寫 16,漏了 `trend-empty`、`split-group-no-expenses`、`split-add-member-empty`、`care-today-summary-setup` —— 漏的原因是只 grep 了 `Empty*` 的 ARB 鍵。

**這是分歧不是重複** —— 沒有一處寫下為什麼要跟隔壁不一樣,所以也無法判斷哪些差異是刻意的。使用者在一次操作裡會走過其中好幾個。

## 決策

### D1:兩層,而不是一層或三層

**第一層「完整引導」** —— 頁/分頁層級,整個畫面沒東西:icon + 標題 + 選填內文 + 選填行動。
**第二層「單行淡字」** —— 卡片/區塊內的空位:`bodyMedium` + `onSurfaceVariant` + 置中。

只做一層會把卡片內的小空位變成佔滿版面的引導;做三層等於沒有標準。

**分層的判準是「這個空的區域是什麼」,不是「現在長什麼樣」** —— 現況本身就是要修的東西,拿它當判準會把錯誤固化。

### D1b:區域怎麼判 —— 看**空掉之後,畫面上還有沒有東西替這塊區域命名**

**「命名」算哪些東西,必須講明,否則這條規則只有寫的人套得出答案。**

- **算**:與空掉的區域**在同一個捲動區內、屬於內容本身**的標題或摘要 —— 卡片的頁首、區塊的小標、就在上面的統計列。
- **不算**:AppBar 標題、分頁標籤、底部導覽、日期/月份切換器。那些是**框架**,它們說的是「你在哪一頁」,不是「這一塊是什麼」。

沒有這一條,`finance_transactions_tab` 會被判錯:它的空分支只回傳一個引導,而 scaffold 的 AppBar 標題正好就是「明細」—— 照字面讀就是「有東西命名了這塊區域」,判成第二層。同樣的讀法會翻掉另外六個站點。**判別力必須來自文字,不是來自套用的人。**

D1 說「依區域判」,但「區域」本身需要一個可檢查的判準,否則兩個相鄰的畫面
會被判成相反的兩層 —— review 就是這樣抓到的:財務總覽的預算卡內註記(第二層)
與當月引導(第一層)只差 16dp,兩者回答的是同一個「新帳號、還沒有東西」。
而讓 `split_tab` 的「群組」區塊變成第二層的那套區域論證,表面上也適用於
財務總覽的當月引導。

**判準:把這塊空掉的東西拿走之後,畫面上是否還留著替它命名的標題/表頭/摘要?**

- **留著 → 第二層。** 這個地方已經自我介紹過了(「預算」「群組」「近期活動」
  「本日運動總分鐘」),空狀態只需要補完那句話 —— 一行淡字就夠。
- **沒留著 → 第一層。** 沒有別的東西說得出這塊是什麼,空狀態就得自己介紹:
  icon 說哪一種空、標題說這是什麼地方、內文與行動說下一步。

逐站點對照(全部一致,沒有例外):

| 站點 | 空掉時還在的命名 | 層 |
|---|---|---|
| `budget_card` | 卡片表頭「預算」 | 2 |
| `goal_card` / `trend_card` | 卡片表頭 | 2 |
| `care_adherence_card` | 卡片表頭 + 7/30/90 選擇器(1.1b 用的就是這個論證) | 2 |
| `exercise_screen` | 上方的當日總分鐘卡 | 2 |
| `menstrual_screen` | 月曆 + 統計卡 | 2 |
| `today_screen` 餐別 | 餐別標題 | 2 |
| `split_tab` 群組 / 近期活動 | 區塊標題(**在 isEmpty 分支之外**渲染) | 2 |
| `group_detail` 支出 | 「支出」區塊標題 | 2 |
| `finance_overview` 當月 | **沒有** —— 月份導覽只說「哪一個月」,預算卡只說「預算」 | 1 |
| `finance_transactions_tab` / `split_tab` 整頁 / `friends` / `networth` / `care_*` / `food_search` / `split_activity_section` | **沒有** | 1 |

所以財務總覽的當月引導**留在第一層**,`split_tab` 的群組區塊**留在第二層**,
兩者不是同一種區域 —— 差別不在看起來像什麼,在於「群組」那個標題與它的
「建立群組」按鈕是在 `isEmpty` 分支**外面**畫的,拿掉註記那塊區域依然被命名;
財務總覽拿掉引導之後,整個分頁沒有任何一處提到「這個月的收支紀錄」。

**這條判準是可以測的,不是說法**:兩邊各有一條測試釘住它 ——
`split_tab_test` 斷言群組標題與其按鈕在空的時候仍在畫面上;
`finance_overview_tab_test` 斷言預算註記在有表頭的卡片內、當月引導不在任何
卡片內。任一邊被改成另一層,對應那條就紅。

**這條判準不覆寫 D1,是 D1 的細則。** 若之後有站點兩邊都說得通,先問「使用者
看不到這個空狀態時,他還知道這塊是什麼嗎?」

### D2:以 `food_search` 的 `_ResultsMessage` 為基礎,但**不能原樣搬**

它已經是參數化的形狀(icon / title / 選填 body / 選填 action / titleColor),是這個 repo 唯一寫過的抽象。但直接抽出來會壞掉兩件事:

**(a) 它把 Column 包在 `SingleChildScrollView` 裡**(`food_search_screen.dart:574`,32/24 padding)。第一層的多數目標是 `ListView` 的直接子項(`care_items_screen:261`、`finance_overview_tab:116`、`split_activity_section:249`)或在 `LedgeCard(padding: 20)` 裡 —— **巢狀的垂直 viewport 在那裡會拿到無界高度而 assert**。

**共用元件是裸的 Column,捲動留在呼叫點。**

**(b) `titleColor` 不是空狀態的參數,是錯誤狀態的。** `_ResultsMessage` 同時渲染 reauth(`:318`)與載入錯誤(`:329`,`titleColor: colorScheme.error`)。所以「把它抽成空狀態元件」跟「只碰空狀態」是矛盾的。二選一,**apply 要明確選並寫理由**:
- 把它抽成**通用的置中訊息狀態**,錯誤與 reauth 一起搬 —— 但那會與 `AsyncStateScaffold` 既有的 reauth 職責重疊(已在 shared-widgets 規格裡)。
- 或 **food_search 保留一份私有的**,共用元件只服務空狀態,那邊什麼都不刪。

### D2b:第三種形狀是既成事實,不是開放題

「兩個行動」的缺口比原本寫的大:

- **`care_history`** 的空狀態**有兩個按鈕**(加寬期間 / 去管理,間距 8),而且標題與內文依 `atLongest` 變化 —— 第一版的表把它寫成「單一按鈕的完整引導」,**錯的**。
- **`split_tab`** 有**三個**行動。

兩個站點需要次要行動。**所以第一層要支援選填的次要行動**,而不是留給 apply 硬塞或悄悄跳過。

### D3:不引入 Mascot

**理由只有一個,而且是這一個**:icon 能表達**哪一種空**(`search_off` = 找不到 / `event_note_outlined` = 還沒排 / `favorite_border` = 還沒收藏),吉祥物全部一樣。空狀態最需要傳達的就是「哪一種空」。

**第一版還寫了另一個理由,那個是錯的**:我說「repo 把吉祥物保留給達成」。實際上 6 個用法裡 **4 個是頁首裝飾**(登入、註冊、首頁,以及**就在這些畫面上方的** `tracker_day_nav_header`),只有 `care-today-celebration` 與 summary card 那兩處是慶祝。所以「吉祥物 = 達成」不是這個 repo 的既有語彙,不能拿來當論證。

### D4:有 `Key` 的站點要保住它 —— 但不是每個站點都有

**先確認哪些真的是約束**:`today_screen` 的餐別空狀態(`today_screen.dart:520`)**沒有 key**,測試是用 `find.text` 定位的(`today_screen_test.dart:1193`);`friends` 的 key 由呼叫點提供;`trend-empty` 與 `split-empty-needs-friends` 沒有任何測試在用。

真的是約束的那些,既有測試靠它們定位。**這是這個 change 最容易靜默弄壞的東西** —— 換掉 widget 之後 key 沒接上,測試會因為找不到而紅(那還好),或者更糟:key 接到了外層而不是原本那個節點,測試照樣綠但斷言的東西變了。

`_ResultsMessage` 已經有 `stateKey` 參數,形狀是對的。

### D5:視覺會變,所以要逐站點說明

這不是純重構,**行為零變化不適用**。每一個站點都要寫下:歸到哪一層、為什麼、視覺上變成什麼。**「跟其他的一致」不是理由** —— 那是結論,理由要是「這個區域是頁層級/卡片內」。

**已知的判斷難點**:
- `budget_card`(卡片內,但有行動鈕)—— 卡片內的空位配一個行動鈕,是第一層還是第二層?
- **`split_tab` 有三個行動同時出現**(`:487` 加好友、`:494` cta、`:502` 建群組)。D2b 給的是**一個**選填的次要行動 —— **主要+次要表達不了三個**,所以這一項仍然開放。上一版把它劃掉說「D2b 已解決」是錯的。要嘛第一層收一串行動,要嘛 split_tab 是第三種形狀,**apply 要決定並寫理由**。
- `finance_transactions_tab`(分頁層級,但現在只有一行沒淡化的字)—— 依區域判是第一層,但它現在沒有 icon 也沒有行動。

**這些 apply 要各自做決定並寫理由**,不要硬塞。

### D5b:兩個站點**明確排除**,不納入這次的標準

**`care_today_summary_card` 的 `care-today-summary-setup`** —— 它在 `slots.isEmpty` 時顯示,但**不是一段空狀態文字,是一個可點擊的引導橫幅**(`LedgeCard > ClipRRect > Column > InkWell > Row`,帶 `Icons.add_circle_outline`)。

- 套第二層會**刪掉它的 icon 與點擊目標** —— 那個點擊是它存在的理由。
- 套第一層會在**卡片內部**展開一個頁層級的引導。
- 而且有 **8 個測試**綁著它。

**它是「還沒設定,點這裡去設定」的入口,不是「這裡沒有東西」的說明。** 兩層標準都不該涵蓋它,強行套用會弄壞一個能用的東西。**不動它**,並在 tasks 明列為排除項,免得下一輪 review 或下一個人以為是漏掉的。

**`group_detail_screen` 的 `split-add-member-empty`** —— 它在 `AlertDialog` 的 body 裡。對話框內部的空位既不是頁層級也不是卡片內,而且對話框有自己的尺寸限制。同樣**不動**,理由記下來。

**排除不是「以後再說」,是判斷結果。** 若之後要收編它們,需要的是第三種形狀的設計,不是把它們硬塞進現有兩層。

## UI/UX 設計

### 使用者路徑

**誰/情境**:新使用者第一次進 app,或既有使用者進到還沒用過的功能。

**主路徑**:進到一個沒有內容的畫面 → 看到這個畫面是做什麼的、以及下一步 → 按下行動 → 開始使用。

**現況(壞掉的)**:有些畫面給完整引導,有些只給一行「還沒有紀錄」,而且字體大小、顏色、間距各不相同。使用者無從得知「這裡是空的」跟「這裡壞了」的差別。

### 介面與一致性

- **完整引導**:icon 48 + 12 + titleMedium + 4 + bodyMedium(淡)+ 16 + FilledButton。這是四個站點已經在用的形狀,以它為準。
- **單行淡字**:bodyMedium + onSurfaceVariant + 置中。
- **icon 由呼叫點提供** —— 它表達的是「哪一種空」,共用元件不該猜。

### 狀態設計

空狀態與 **loading**、**錯誤** 是三件不同的事,這個 change **只碰空狀態**。不要把載入中或錯誤順手改成空狀態的形狀。

### 可及性/理解性

- 完整引導要能被讀成「這裡沒有東西 + 這是什麼 + 可以做什麼」。
- 單行淡字的對比度:`onSurfaceVariant` 在這個主題下的對比要確認(`stale_notice.dart` 有一段先例,它為了對比度**沒有**用 `colorScheme.primary`)。

## 驗收(可觀察的行為)

1. WHEN 頁/分頁層級的畫面沒有內容,THEN 顯示 icon + 標題(+ 有的話,內文與行動)。
2. WHEN 卡片/區塊內的區域是空的,THEN 顯示一行淡色置中文字,不是整頁引導。
3. WHEN 完整引導出現在 320dp × 文字比例 2.0,THEN 文字不被裁切、行動鈕仍可點擊。
4. 原本帶著 `Key` 的站點,那個 key 仍然定位到樹上的同一處(沒有 key 的站點不適用 —— 見 D4)。

## 風險

- **判錯層** —— 把卡片內的空位做成完整引導,會在一個有內容的畫面中間插進一個佔滿版面的東西。
- **Key 接錯層** —— 測試照樣綠但斷言的東西變了。**要逐一確認 key 落在原本那個節點上**,不是「測試通過就好」。
- **窄螢幕,而且「守不住」這句只對一部分成立**:Column 溢出**有界的**盒子**會**丟 `FlutterError`,所以 `finance_transactions`(在 scaffold body 的 `Center` 裡)與 `trend_card`(`SizedBox(height: 200)`)其實守得住;`ListView` 子項那些才守不住。**改完之後這個分佈會變**(元件換了、祖先可能換了),所以不能沿用今天的判斷 —— 要逐站點確認哪些會丟、哪些要靠量測。PR #128 剛因為「守門存在但不會丟」漏掉一個 blocking。
- **視覺變動沒有「對照 main」這條退路**(因為就是要變),所以每一處的變化都要在 tasks 裡寫下預期,再用測試釘住。
