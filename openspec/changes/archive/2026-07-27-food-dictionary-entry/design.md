# 食物字典：一個不必先選餐的查詢入口（issue #88）

## 問題

[issue #88](https://github.com/loftapartment/life-os/issues/88)：「[食物字典] 多一個容易查詢的入口」。

食物字典目前**只存在於「加入某一餐」的流程裡**。`FoodSearchScreen` 需要 `meal` + `day` 才能建構，路由 `/health/diet/food-search` 靠 `extra` 帶進來；點任何一列就是加進 tray，底部還有提交按鈕。

所以想查「這東西算幾份」得走：健康 → 飲食 → 選一餐 → 加食物 → 搜尋 → 看到份量 → 然後**小心地退出**（點錯就加進去了）。

**順序是反的**：你得先承諾「要記到哪一餐」，才能查「這東西算幾份」。而真實的查詢情境 —— 在超市、看菜單、決定要不要吃 —— 根本還沒到選餐那一步。

## 設計決策

### D1 — 入口放飲食頁的 AppBar，用純圖示

字典本來就屬於飲食，放在那裡語意最順：你在看今天吃了什麼、想查一下某個食物，不用離開脈絡。

不放「記錄」分頁：那六格（飲食／飲水／生理數值／運動／排便／生理期）**全是「記錄某件事」**，字典是「查」，並列會讓人以為點進去要記錄什麼。也不放總覽：總覽講的是「今天的狀態」，字典是工具，而且那頁已經很滿。

AppBar 目前已有一個帶文字的「目標」按鈕，所以查詢用**純 `IconButton`**（省寬度）。兩者並存在 320／360 寬下是否溢出，用**自動化測試**守住（repo 已有 `setSurfaceSize` + `addTearDown` 的 overflow 測試慣例），不靠人工看。若真的擠，優先把「目標」也收成純圖示 —— 而不是把查詢挪走。

### D2 — 重用 `FoodSearchScreen`，把 `meal` 變成可選

同一個畫面，差別只在「要加到哪一餐」是**進來前就決定**還是**離開前才決定**：

| | 從某一餐進來（現況） | 從字典入口進來（新） |
| --- | --- | --- |
| `meal` | 已指定 | `null` |
| 標題 | 「加入 {餐別}」 | 「食物字典」 |
| 點食物 | 加進 tray | 加進 tray（相同） |
| 還在瀏覽時（沒搜尋、tray 為空） | 提交按鈕在（disabled） | **隱藏**提交按鈕與常駐的手動輸入連結 |
| 送出 | 直接送 | **先問加到哪一餐**，再送 |

「純查詢時畫面乾淨」**不是免費得到的，要真的改**：現況只有 `_TrayPanel` 被 `if (createMeal.tray.isNotEmpty)` 包住；提交按鈕在 `bottomNavigationBar` 裡是**無條件渲染**、tray 空時只是 disabled（文案仍為「完成（0）」），「找不到？手動輸入」連結也一直在。

所以 `meal == null` 且 tray 為空時，要**隱藏**提交按鈕與手動輸入連結，而不是讓它們 disabled —— disabled 的按鈕仍在說「這裡是拿來記錄的」，而這個入口的前提是使用者只想查。一旦點了食物，tray 與提交按鈕一起出現：記錄的意圖是使用者自己表達的，不是介面預設的。

（既有測試沒有任何一條斷言空 tray 時提交按鈕存在，所以隱藏它不會讓既有測試退化。）

**但「隱藏」只到常駐控制項為止。**「找不到？手動輸入」這句文案本來就是為「搜尋不到」寫的，
把它跟提交按鈕一起無條件砍掉，等於在使用者最需要出口的那一刻把出口收走：字典裡查不到某個食物時，
畫面上沒有解釋也沒有下一步，想手動輸入還得先隨便點一個不相干的食物讓控制項冒出來、輸入完再刪掉。
所以規則是**常駐 vs 有脈絡**，不是「有 vs 沒有」：常駐的手動輸入連結在瀏覽時隱藏；
**搜尋回來是空的時候，手動輸入出現在那個空狀態裡** —— 由使用者自己的搜尋行為觸發。
反過來，已經有常駐連結的情況（指定餐進入、或字典模式下 tray 已經有東西）空狀態就不再放一次，
否則同一個出口會同時出現兩個。

不另做一個唯讀畫面：那會讓「查到了想記錄」變成死路（退出、選餐、再搜一次），而查詢與記錄本來就是連著的動作。

### D3 — 選餐延到送出時，一次選一餐

`CreateMealController` 的 `meal` 只在 `submit` 的最後一行用到（`_createMeal(..., meal: meal, ...)`），`start(meal)` 只是 seed。所以延後決定在架構上不需要改動資料流，只是把「什麼時候知道 meal」往後移。

選餐用 bottom sheet，選項是三個標準餐 + 一個「點心」。**整個 tray 加到同一餐**，不是每個食物各自選 —— 一次互動而不是 N 次，而且「查了三樣東西要記進不同餐」是罕見情境，那種情況走既有的逐餐流程更直接。

**點心的名稱**要看該日已有哪些餐才能算（`nextSnackName`，在 `snack_naming.dart`，需要 `loc.dietSnackBaseName`）。飲食頁本來就有那份資料，所以進字典時一起帶過去，不讓字典自己再載一次。

`mealNames` 是 **push 當下的快照** —— 若當日的餐點資料還沒載完就進字典，算出的點心名可能併入既有群組。這與飲食頁既有的 `_openAddSnack` 是同一個風險、同一個來源，本 change 不另外處理。

### D4 — 沿用飲食頁當下瀏覽的那一天

飲食頁可以瀏覽過去的日子。從那裡進字典再加入食物，要落在**當時在看的那一天**，不是永遠今天 —— 否則使用者在補記昨天的飲食時，東西會悄悄記到今天。

### D5 — 最愛管理是免費得到的

空查詢時顯示最愛、每列都有愛心，這是 `DictionaryController` 既有行為。所以這個入口天然也是「管理我的常用食物」的地方，不需要另外做。

## 元件

| 檔案 | 改動 |
| --- | --- |
| `DietDayScreen` | AppBar 加查詢 `IconButton`；push 時**比照 `_openFoodSearch` 的三步**：`createMealController.start(...)` 重置 tray、`dictionaryController.clearSearch()`、`await` push 結果為 true 時 `_reloadCurrentDay()` |
| `lib/app.dart` | 新路由 `/health/diet/dictionary`（`extra` 缺席時比照 food-search redirect 回飲食頁） |
| `FoodSearchScreen` | `meal` 改可選、**新增 `mealNames` 參數**（算點心名用）；標題依 `meal` 分岔；**`meal == null` 且 tray 空時隱藏提交按鈕與常駐的手動輸入連結**（現況兩者無條件渲染）；**結果區新增四種狀態**（載入中／失敗＋401 復原／沒有最愛／搜尋 0 結果＋有脈絡的手動輸入）；送出前若 `meal` 未定則開選餐 sheet（sheet 內容可捲動、選完回來先檢查 `mounted`） |

## UI/UX 設計

### 使用者路徑

**主路徑（純查詢）**：飲食頁 → 點 AppBar 的搜尋圖示 → 看到最愛清單 → 搜尋 → 每列顯示份量 → 看完返回。全程沒有任何記錄相關的 UI。

**查了之後決定要記**：同上 → 點一個食物 → tray 出現 → 可再加幾個 → 送出 → 選一餐 → 回到飲食頁看到結果。

**管理常用食物**：同入口 → 搜尋 → 點愛心加入/移除最愛。

**例外路徑**：
- 直接用網址開 `/health/diet/dictionary`（沒有 `extra`）→ redirect 回飲食頁（比照現有 food-search 的處理）。
- 上一次在某一餐的搜尋放棄了、tray 還留著 → 進字典前 `start(...)` 已經把它重置，不會一進去就看到提交區。
- 字典載入／搜尋 401 → **結果區自己呈現** reauth 與「重新登入」。畫面既有的 reauth 區塊掛在
  `createMeal.status`（送出失敗才會出現）而且住在 `bottomNavigationBar` 裡，字典模式下那個
  bottomNavigationBar 是 null —— 所以「沿用既有呈現」在這裡等於零復原路徑，必須另外做。
- 送出失敗 → 沿用既有錯誤處理（bottomNavigationBar 裡的錯誤訊息），tray 保留。

### 介面與一致性

不新增畫面，字典就是既有的搜尋畫面在「還沒選餐」狀態下的樣子。AppBar 圖示用 `Icons.search`，與 app 內其他圖示一樣走主題色。選餐 bottom sheet 比照專案既有的 bottom sheet 慣例（行動裝置上帶文字輸入的對話框改用 bottom sheet 是這個 repo 的既有決定）。

### 狀態設計

- **剛進入**：搜尋欄 + 最愛清單。沒有 tray、沒有提交按鈕。
- **點了食物**：tray 從底部出現，提交按鈕跟著出現 —— 這是畫面上唯一「你正在記錄」的訊號。
- **送出**：選餐 sheet → 送出中 → 成功回飲食頁／失敗保留 tray 與錯誤。

結果區在字典模式下**就是整個畫面**（沒有 bottomNavigationBar、沒有常駐連結），所以它一片空白時
使用者無從分辨「我沒有最愛」「這個字沒找到」「壞掉了」—— 這三件事的下一步完全不同。既有的畫面
沒有任何空狀態（結果區是裸的 `ListView.builder(itemCount: results.length)`，`build()` 也從來
沒讀過 `dictionary.status`），所以這是本 change 要補的，四個狀態各自明說：

| 狀態 | 呈現 | 下一步 |
| --- | --- | --- |
| 載入中（`DictionaryStatus.loading`） | 轉圈 | 等 |
| 載入／搜尋失敗（`error` / `needsReauth`） | 失敗訊息；401 另附「重新登入」 | 重試或重新登入 |
| 沒有最愛、也還沒搜尋 | 「還沒有常用食物」+ 提示可以搜尋、點愛心留住 | 搜尋 |
| 搜尋 0 結果 | 「找不到『X』」（帶上查不到的那個字） | **手動輸入**（僅在沒有常駐連結時） |

比照 repo 既有的空狀態慣例（`careRemindersEmptyTitle/Body`、`careTodayEmpty*`、
`exerciseEmptyLabel`）：圖示 + 標題 + 說明，顏色一律走 `Theme.of(context)`。空狀態本身可捲動，
免得鍵盤彈出把視窗壓短時反而溢出。

選餐 sheet 也一樣要能在被壓短時活下來：預設 modal sheet 上限是螢幕的 9/16，標題 + 四個選項在
矮螢幕或大字級下會超過，被裁掉的正好是最下面的「點心」（= 使用者選不到點心），所以內容包一層
`SingleChildScrollView`。另外選完餐回來要先 `if (!mounted) return;` —— sheet 開著時被登出，
那一餐仍然會被真的存進後端（`care_history_screen.dart` 同形狀的 sheet 已有同樣的防護）。

### 可及性/理解性

查詢圖示要有 tooltip（螢幕閱讀器與長按都會用到）。選餐 sheet 的每個選項是標準 `ListTile`，可直接讀出餐別名稱。標題從「加入 {餐別}」變成「食物字典」是使用者能感知的差別 —— 它告訴你這次不是在記錄。

## 測試策略

- **screen（widget）**：`meal` 為 null 時標題是「食物字典」且**沒有**提交區；點食物後 tray 與提交區出現；送出時開選餐 sheet 並把選到的餐別傳給 controller；`meal` 已指定時行為與今天逐字相同（既有測試不得退化）。
- **入口（widget）**：飲食頁 AppBar 有查詢按鈕且帶 tooltip；點它會 push 到字典路由，並帶上**當下瀏覽的日期**（不是今天）與該日的 mealNames。
- **controller（單元）**：未指定 meal 的 session 可以加入 tray；送出前綁定 meal 後才呼叫 `CreateMeal`；未綁定就送出不會打後端。
- **路由**：`extra` 缺席時 redirect 回飲食頁（比照 food-search 既有測試）。
- **session 乾淨**：在某一餐加了東西、返回、再開字典 → tray 是空的、沒有提交區（守住入口的 `start(...)`）。
- **結果區狀態**：沒有最愛 → 空狀態而不是空白；搜尋 0 結果 → 帶查詢字的空狀態 + 手動輸入（點下去真的開表單）；
  已有常駐連結時（指定餐／tray 非空）空狀態**不**再放一次；載入失敗與「沒有資料」是兩種不同的畫面；401 有「重新登入」且真的登出；載入中是轉圈不是空狀態。
- **窄螢幕**：320／360 寬下 AppBar 不溢出；矮螢幕下選餐 sheet 的最後一個選項仍然點得到。
- **拆掉也不存**：選餐 sheet 開著時畫面被拆掉（登出），選完之後不打後端。
- **既有測試不得退化**：現有的 food-search 測試（從某一餐進入的完整流程）全部維持。

## 不做（YAGNI）

- 「更多」分頁再放一個入口 —— 同一個目的地兩個入口要維護，也可能讓人以為是兩個不同的東西。若之後發現飲食頁那個不夠被發現，再加。
- 每個食物各自選餐 —— 見 D3。
- 唯讀的字典畫面 —— 見 D2。
- 全域搜尋（app 層級）—— 超出 issue 範圍。
- 字典的分類／標籤瀏覽 —— issue 要的是「查詢」，搜尋 + 最愛已涵蓋。
