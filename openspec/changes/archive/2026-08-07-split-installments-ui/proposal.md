# 分帳分期的前端

## Why

後端已經上了(life-os-backend#83/#84),而**使用者完全看不到也用不到** —— 分帳表單沒有任何設定還款時程表的地方,餘額卡不顯示進度,而分期產生的每一期在帳本明細裡跟普通的分帳鏡像長得一模一樣(12 筆 500 沒有任何區別)。

## What Changes

- **分帳表單可以為單一分攤者設定還款時程表**(期數;每期金額由系統算)。
- **餘額卡顯示每個時程表的進度**:第 N/M 期、每期金額,**一個時程表一行**。
- **帳本明細的分帳鏡像標出「第 N 期」**。

## 三個裁定

### 除不盡:自動微調分攤額,並且說出來

後端要求 `期數 × 每期金額 === 分攤額`,不吃餘數。6,100 分 12 期除不盡,所以 UI 把該分攤者的分攤額調到最近的可整除值(6,096),**差額移到別人身上**。

**吸收差額的順序是有定義的,不是隨便挑一個人**:

1. 付款人自己的分攤(調自己的份最不需要解釋)
2. 其他**沒有排程**的分攤者(動一個已排程的分攤額會讓那個人的時程表也跟著要重算)
3. 兩者都沒有 → **擋下**,並列出最接近的可行期數(10 期 × 610、20 期 × 305)

**調整一定顯示在畫面上**(`6,100 → 6,096`),不靜默改別人的數字 —— 靜默改是這個 repo 反覆出過的那類 bug。

### 帳本明細:「第 N 期」,沒有總期數

分帳分期的鏡像有 `installment_no`,但**沒有 `plan_id`** —— 那是「他跟我」,不是「我跟銀行」,沒有分期計畫可查,所以拿不到總期數。沿用財務分期已經有的 `financeInstallmentPeriodOnly`(「第 N 期」)文案,不新造。

**這推翻了現有的判斷式**:`finance_transaction_row.dart` 與 `add_transaction_sheet.dart` 都用 `planId != null` 當「這是分期」,而分帳分期永遠是 `planId == null`。判斷要改成 `installmentNo != null`,計畫層級的動作(前往計畫)才留在 `plan != null`。installments-ui 那輪已經把「兩者皆非 null」寫進測試,但它守的是**有 plan 的那半**;`installmentNo` 有而 `planId` 沒有的形狀當時產不出來,現在產得出來了。

### 餘額卡:一個時程表一行

後端逐筆分帳回傳(`schedules` 是陣列,不是單一物件)—— 同一個朋友同幣別可以有兩個時程表,而把它們合成一個數字正是 #84 修掉的 bug。前端不要把它折回去。

## 依賴:後端 #85 必須先進

`GET /api/split/expenses/:id` 原本**不回傳 schedule**,而 `PATCH` 送的是整份分攤名單 —— 客戶端讀不到的東西就送不回去,所以**每一次編輯都會把時程表弄掉**,而弄掉的後果是持有者被重複收費(12 期 + 一筆總額)。#85 修了鏡像重寫與讀取形狀兩半。

**沒有 #85 的話這個 change 做出來就是一個會弄壞朋友帳本的功能。**

## Impact

- `ExactShareInput` 加 `schedule`;`SplitShare` 讀取模型加 `schedule`;`CurrencyBalance` 加 `schedules`。
- `split_expense_sheet.dart`(798 行)加逐分攤者的時程表控制;差額吸收是**純函式**,放 domain,不是塞在 widget 裡。
- `split_tab.dart` 的餘額卡多一段。
- `finance_transaction_row.dart` / `add_transaction_sheet.dart` 的分期判斷式改口徑。

## 明確不做

- **均分模式不支援時程表**(後端的 `schedule` 只存在於 `mode: "exact"` 的分攤上)。表單要說出來,不是預設值一改就靜靜失效。
- **不做「記錄這一期還了」** —— 還款仍然走現有的結清流程,而一期的日期到了不等於還了(後端明說)。
- **不顯示某一期是否已還** —— 後端沒有這個資訊(進度是日曆算的,不是結清算的)。
