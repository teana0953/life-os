# 設計:分帳的「變更紀錄」分頁

## 為什麼

後端(backend PR #72)已經在記錄八種分帳異動的事件時間軸,含**刪除**與**修改**——那正是使用者現在完全看不到、卻會改變自己欠多少的事:一筆支出被刪掉之後,列與 shares 都消失,使用者只會發現餘額變了。

`GET /api/split/activity?limit=&cursor=` 已經上線,回傳依可見範圍過濾、時間倒序、keyset 分頁的時間軸。

## 這不是現有那份清單

分帳頁現在已經有一段叫「最近活動」的東西(`split_tab.dart:110-116`),**但它是不同的東西**:

| | 現有的「最近活動」 | 新的「變更紀錄」 |
|---|---|---|
| 內容 | 目前**存在**的支出 + 還款 | **發生過**什麼,含已刪除的 |
| 排序 | 使用者填的消費日期 (`day`) | 記錄時間 (`created_at`) |
| 可否編輯 | 每列可點進去編輯 | 不可(那筆可能已不存在) |
| 有誰做的 | 無 | 有 actor |

**兩者都留著**(使用者決定):想改一筆去主頁,想知道發生了什麼去變更紀錄。名字也要分開——現有的維持「最近活動」,新的叫「變更紀錄」。

## 決策

### D1:分頁怎麼放

分帳分頁目前是一個長 `ListView`(餘額卡 → 群組 → 最近活動)。新增一層分頁:**總覽 / 變更紀錄**。

實作形狀留給 apply 決定(`TabBar` vs `SegmentedButton`),但要求:

- **不要動 `FinanceScaffold` 的底部導覽**(總覽/記錄/趨勢/更多),那是第三層,會太深。
- **分頁切換要在 `SplitTab` 的 loading / 錯誤 / 空狀態分支之上**。放在下面的話,總覽的載入失敗會把變更紀錄也一起變成錯誤頁,而它們是兩份獨立的資料。
- **`split-fab`(記一筆)在變更紀錄分頁要怎樣?** 做決定並寫理由——那是唯讀的分頁,留著一個「記一筆」的浮動鈕是可以的(它不是那個分頁的動作,是整個分帳的),隱藏也是可以的,但不能沒想過。

### D2:文案渲染 —— 這是這個 change 唯一真正困難的地方

八種事件 × 「我是不是 actor」= 十六種文案,再加上**還款的方向**:

後端存的 `actor_is_payer` 是**相對於 actor** 的布林,而讀者可能是三種角色之一:

| 讀者是 | `actor_is_payer` | 應該顯示 |
|---|---|---|
| actor | true | 你付給 Ben |
| actor | false | Ben 付給你 |
| counterpart | true | Amy 付給你 |
| counterpart | false | 你付給 Amy |
| 第三人(群組成員) | true | Amy 付給 Ben |
| 第三人 | false | Ben 付給 Amy |

**六種情況,而且寫錯了畫面看起來完全正常、只是方向相反。** 這是這個 change 最容易出錯的地方,而且錯了會讓使用者以為別人還了錢(或以為自己還沒還)。

**要求:抽成一個純函式**(輸入:事件、`selfUserId`;輸出:要顯示的角色與方向),**用表格驅動的測試把六種情況全部釘住**,而且每一種都要有能讓它單獨變紅的突變。不要把這段邏輯散在 widget 的 build 裡。

### D3:分頁載入

後端是 keyset cursor。**`next_cursor` 不是 has-more 旗標**:它只在**頁面不滿**時才是 `null`;最後一頁剛好滿的話會回一個 cursor,**下一次請求才回空**(後端刻意不做「多查一列」,見 `list-activity.ts:64-66`)。所以正常結束的路徑會多打一次、拿到空頁。這不是要修的東西,是要在前端寫清楚的行為。

- 第一頁在分頁被開啟時載入,**不是** app 啟動時(這條時間軸會無限成長)。
- 捲到底載下一頁。**拿到 `next_cursor == null` 之後不要再打**,而且要有測試釘住——重複打同一個 cursor 是很容易寫出來的無限迴圈。
- **空的最後一頁不是錯誤、也不是空狀態**:已經載到的內容要留著。

**`limit` 的實際行為(從後端讀出來的,不要猜)**:未帶時預設 50,超過 100 會被靜默夾住,非數字回 400。前端不要一次要很多。

### D3b:這個 repo 沒有無限捲動的先例

`lib/` 裡**沒有 load-more 的既有實作**——但不要照著第一版寫的「連 `ScrollController` 都沒有」去找,那句是假的:`food_search_screen.dart:619/698/758` 就有一個在讀 `maxScrollExtent`,那是最接近可以參考的地方。真正沒有的是「捲到底自動載下一頁」這個行為。所以:

**「捲到底之後不再請求」這條測試很容易是空的**——如果測試視窗裡的清單根本沒有溢出,觸發條件永遠不會發生,那條測試在**任何**實作下都會通過。**必須先有一個正面對照**:證明捲到底**會**觸發下一頁的請求,再證明沒有下一頁時不會。兩條缺一不可。
- 載入中/錯誤/空狀態沿用既有慣例(`card_error_retry.dart`、`AsyncStateScaffold` 那套)。

### D4:token 要用 provider

PR #126 之後,畫面拿的是 `IdTokenProvider`(用時才解析),**不是** `String`。新的 controller 與畫面照那個形狀寫,不要複製任何 `await repository.idToken() ?? ''` 的 inline 版本(`guardedIdToken` 的 doc 明文禁止)。

### D4b:八種事件都要說出內容,不能只說「有人改了」

後端在每一筆修改上記了 `previous_amount`,**就是為了不讓修改被渲染成一句沒有內容的「某人修改了這筆」**。前端要用上它:金額**有變動**時顯示**改前 → 改後**。

**但 `previous_amount` 不是「金額有變」的旗標** —— 後端**每一次**修改都寫它,包含只改了描述、日期或參與者的那些(後端的型別註解明說了)。所以無條件顯示會渲染出「$2000 → $2000」。判斷要用 `previousAmount != amount`,而不是 `previousAmount != null`。

三種群組事件(建立群組、加入成員、封存群組)同樣要有各自的文案,不能落到一個泛用的 fallback。

**八種都要列進 5.2 的文案清單**,不要只做支出與還款那五種。

### D4c:顯示名稱的 fallback

`counterpart_display_name` **可為 null**,用 `?? splitUnknownMember` 接住即可。

`actor_display_name` **不是 nullable** —— 後端在沒有名字時把它填成**原始 UUID**(`drizzle-split-activity-repository.ts:86`)。所以 `actorDisplayName ?? splitUnknownMember` 那個 `??` **永遠不會觸發**,而 UUID 照樣顯示出來:那是一個不可能失敗的守門。**判斷式是 `actorDisplayName == actorUserId`。**

兩者的共同要求:**不要讓 UUID 出現在畫面上**,而且那條測試要能被突變弄紅(把判斷改回 `??`)。

### D5:不可編輯,而且要看得出來

變更紀錄的每一列**不可點擊**。已刪除的事件更是連目標都不存在。不要做成看起來可點但沒反應。

## UI/UX 設計

### 使用者路徑

**誰/情境**:群組裡的使用者,發現自己的餘額變了,想知道為什麼。

**主路徑**:分帳 → 變更紀錄 → 看到「Amy 刪除了 晚餐 $2000」→ 知道發生了什麼。

**例外路徑**:沒有任何變更(新使用者)→ 空狀態;載入失敗 → 錯誤 + 重試;捲到底且沒有更多 → 不再載入,也不顯示無止盡的 spinner。

### 介面與一致性

- 每列的形狀對齊既有的 `SplitExpenseRow` / `SettlementRow`(這兩個是分帳現有的列語彙),但**不帶編輯 affordance**。
- 時間顯示:repo 的實際慣例是 `parseInstant` + `mediumDateLabelOrDash`,時分則是 inline 的 `DateFormat('HH:mm')`(見 `friends_screen` 的私有 `_localDateTimeLabel`)。**第一版寫的「既有的日期格式 helper」指的是一個不存在的東西**——照 `friends_screen` 那個形狀做。
- 「你」的呈現要一致:主詞是自己時用「你」,不是顯示自己的名字。

### 狀態設計

- **loading**:第一頁載入時的中心 spinner;載下一頁時是列表底部的小 indicator,**不要**把已載入的內容換掉。
- **錯誤**:第一頁失敗 → 錯誤 + 重試;下一頁失敗 → 保留已載入的,底部顯示可重試的提示(不要把整頁變成錯誤)。
- **空狀態**:訊息 + 說明(這個 app 的完整引導形狀),不要空白頁。
- **reauth**:沿用 `AsyncStateScaffold` 的出口(PR #125)。

### 可及性/理解性

- 每列要能被螢幕閱讀器讀成一句完整的話(誰、做了什麼、什麼金額、什麼時候),而不是散落的片段。
- 刪除類的事件要讀得出「這是已經被刪掉的東西」,否則聽起來像現存的支出。

## 驗收(可觀察的行為)

1. WHEN 分帳的變更紀錄分頁被開啟,THEN 顯示依時間倒序的事件,最新在最上面。
2. WHEN 某個事件的 actor 是自己,THEN 主詞顯示為「你」;否則顯示對方的名字。
3. WHEN 事件是還款,THEN 顯示的方向對**三種讀者角色**(付款方、收款方、群組第三人)都正確。
4. WHEN 捲到底且 `next_cursor` 為 null,THEN 不再發出請求。
5. WHEN 事件是刪除,THEN 仍顯示被刪除項目的金額與描述,且該列不可點擊。

## 風險

- **方向渲染錯了看起來完全正常。** 六種情況要表格驅動 + 突變驗證(D2)。
- **分頁的無限迴圈**:`next_cursor` 為 null 之後還打、或重複打同一個 cursor。要有測試。
- **這條時間軸會無限成長**,而後端的可見範圍述詞目前不可 sargable(backend 的 follow-up)。前端不要預設載很多頁。
- 新增的 ARB 字串會很多(八種事件 × 你/別人 × 還款方向)。**兩個語系都要補齊**,而這個 repo 有一個既有 issue(#99)是 ARB parity 零測試。
