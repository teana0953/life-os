## Why

The backend now lets the assistant read care records — `get_care_today`,
`get_care_range` and `list_care_items` ride the **existing**
`X-Assistant-Health: on` opt-in (life-os-backend PR #125, archived change
`assistant-read-care-records`). The app already sends that header whenever the
user has opted in, so the capability is live today with no frontend logic
change at all.

What is not live is the copy. Every user-facing sentence about this switch
still says "health and diet records" and the settings disclosure still names
exactly three record types — menstrual cycles, blood glucose, vital signs.
Care records (medication doses, rehab sessions and the rest of the care slots)
are now sent to Google's Gemini under a consent whose own disclosure never
mentions them. That is both a consent-accuracy problem and a discoverability
one: 照護 is the record type this product's owner asks about most, and nothing
on screen tells anyone the assistant can answer about it (issue #233,
frontend side).

## What Changes

Copy only. No new switch, no new header, no controller/repository/use-case
change, no test-fixture behavior change beyond the strings themselves.

- `settingsAssistantHealthLabel` — the switch label widens beyond "health and
  diet records" to cover care records, so the thing the user is consenting to
  is named on the control itself.
- `settingsAssistantHealthDisclosure` — the disclosure's explicit record-type
  list gains care records, named as specifically as menstrual cycles, blood
  glucose and vital signs already are. Destination (Google's Gemini),
  free-tier training use (stated once in `settingsAssistantTrainingNotice`)
  and the sign-out revocation are unchanged.
- `assistantEmptyHintNoContextMixed` / `assistantEmptyHintNoContextMixedConsentOff`
  — the home entry's health half names care records too, in both the
  consent-on (outright) and consent-off (conditional) wordings.
- `assistantEmptyHintHealth` / `assistantEmptyHintHealthNoDay` — the health
  entry's hint names care records; the ask-for-a-period nudge on the no-day
  variant is unchanged.
- `assistantHealthAccessOff` — the health-entry refusal names care records
  among what the assistant cannot read while the consent is off, so the
  refusal covers the same ground the consent does.
- The `description` of every key above is updated in `app_en.arb` to state the
  new semantics, since those descriptions are the translator-facing contract
  and currently pin the old three-type list.
- All three ARBs stay in sync: `app_en.arb` (template, with descriptions),
  `app_zh_Hant.arb`, and `app_zh.arb` (fallback base — it carries the five
  assistant keys but not the two settings keys, so only the assistant five
  change there). `flutter gen-l10n` is re-run and `lib/l10n/generated/` is
  committed with the diff.

Not in this change: any care **write** or proposal from the assistant, any
reminder/push-record copy (those stay unreachable in both opt-in states
server-side, so claiming them would be a lie), a separate care opt-in, and any
change to the `X-Assistant-Health` header logic or to when it is sent.

### Modified Capabilities

- `assistant-health-consent`: the requirement "The settings control states what
  is sent and where" changes — the record types the disclosure must name
  explicitly, and the scope the switch label states, both widen to include care
  records. The purpose statement widens with it. Nothing about how the consent
  is stored, revoked, or sent changes.
- `assistant-entry-context`: two requirements change — "The empty-state hint
  matches the entered module" (health-entry and home-entry hints must name care
  records alongside health and diet records, in both consent states) and "A
  health entry with health access off is told so and given the way out" (the
  refusal must name care records among what cannot be read). The controls,
  live-region behavior, example prompts and period nudges are unchanged.

## Impact

- `lib/l10n/app_en.arb` — 7 strings (5 assistant + 2 settings) and their 7
  `@key.description` entries.
- `lib/l10n/app_zh_Hant.arb` — the same 7 strings.
- `lib/l10n/app_zh.arb` — the 5 assistant strings (it carries no settings keys).
- `lib/l10n/generated/*.dart` — regenerated by `flutter gen-l10n`, committed.
- `test/contexts/settings/presentation/settings_screen_test.dart` and
  `test/contexts/assistant/presentation/assistant_screen_test.dart` — these
  assert against `AppLocalizations` lookups, so they follow the copy for free;
  the one place asserting a **literal** (`assistant_screen_test.dart:995`)
  needs its literal updated.
- No Dart under `lib/contexts/` changes: `settings_screen.dart` and
  `assistant_screen.dart` already render these keys and pick between them on
  the existing `healthEnabled` flag.
- No backend change (already shipped), no new dependency, no schema change.
