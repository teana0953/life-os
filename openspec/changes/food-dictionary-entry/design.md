# 食物字典：一個不必先選餐的查詢入口（issue #88）

## 問題

[issue #88](https://github.com/loftapartment/life-os/issues/88)：「[食物字典] 多一個容易查詢的入口」。

食物字典目前**只存在於「加入某一餐」的流程裡**。`FoodSearchScreen` 需要 `meal` + `day` 才能建構，路由 `/health/diet/food-search` 靠 `extra` 帶進來；點任何一列就是加進 tray，底部還有提交按鈕。

所以想查「這東西算幾份」得走：健康 → 飲食 → 選一餐 → 加食物 → 搜尋 → 看到份量 → 然後**小心地退出**（點錯就加進去了）。

**順序是反的**：你得先承諾「要記到哪一餐」，才能查「這東西算幾份」。而真實的查詢情境 —— 在超市、看菜單、決定要不要吃 —— 根本還沒到選餐那一步。

## 設計決策

### D1 — 入口放飲食頁的 AppBar，用純圖示

字典本來就屬於飲食，放在那裡語意最順：你在看今天吃了什麼、想查一下某個食物，不用離開脈絡。

不放「記錄」分頁：那六格（飲食／飲水／生理數值／運動／排便／生理期）**全是「記錄某件事」**，字典是「查」，並列會讓人以為點進去要記錄什麼。也不放總覽：總覽講的是「今天的狀態」，字典是工具，而且那頁已經很滿。

AppBar 目前已有一個帶文字的「目標」按鈕，所以查詢用**純 `IconButton`**（省寬度）。窄螢幕上兩者並存需要實測，若真的擠，優先把「目標」也收成純圖示 —— 而不是把查詢挪走。

### D2 — 重用 `FoodSearchScreen`，把 `meal` 變成可選

同一個畫面，差別只在「要加到哪一餐」是**進來前就決定**還是**離開前才決定**：

| | 從某一餐進來（現況） | 從字典入口進來（新） |
| --- | --- | --- |
| `meal` | 已指定 | `null` |
| 標題 | 「加入 {餐別}」 | 「食物字典」 |
| 點食物 | 加進 tray | 加進 tray（相同） |
| tray 為空時 | 不顯示提交區（現況行為） | 同 —— 所以純查詢時畫面自然乾淨 |
| 送出 | 直接送 | **先問加到哪一餐**，再送 |

「tray 為空就不顯示提交區」是既有行為（`if (createMeal.tray.isNotEmpty)`），所以純查詢的人從頭到尾看不到任何記錄相關的 UI；一旦點了食物，tray 才出現 —— 記錄的意圖是使用者自己表達的，不是介面預設的。

不另做一個唯讀畫面：那會讓「查到了想記錄」變成死路（退出、選餐、再搜一次），而查詢與記錄本來就是連著的動作。

### D3 — 選餐延到送出時，一次選一餐

`CreateMealController` 的 `meal` 只在 `submit` 的最後一行用到（`_createMeal(..., meal: meal, ...)`），`start(meal)` 只是 seed。所以延後決定在架構上不需要改動資料流，只是把「什麼時候知道 meal」往後移。

選餐用 bottom sheet，選項是三個標準餐 + 一個「點心」。**整個 tray 加到同一餐**，不是每個食物各自選 —— 一次互動而不是 N 次，而且「查了三樣東西要記進不同餐」是罕見情境，那種情況走既有的逐餐流程更直接。

**點心的名稱**要看該日已有哪些餐才能算（`nextSnackName`）。飲食頁本來就有那份資料，所以進字典時一起帶過去，不讓字典自己再載一次。

### D4 — 沿用飲食頁當下瀏覽的那一天

飲食頁可以瀏覽過去的日子。從那裡進字典再加入食物，要落在**當時在看的那一天**，不是永遠今天 —— 否則使用者在補記昨天的飲食時，東西會悄悄記到今天。

### D5 — 最愛管理是免費得到的

空查詢時顯示最愛、每列都有愛心，這是 `DictionaryController` 既有行為。所以這個入口天然也是「管理我的常用食物」的地方，不需要另外做。

## 元件

| 檔案 | 改動 |
| --- | --- |
| `DietDayScreen` | AppBar 加查詢 `IconButton`；push 時帶當日 `day` 與 `mealNames` |
| `lib/app.dart` | 新路由 `/health/diet/dictionary`（`extra` 缺席時比照 food-search redirect 回飲食頁） |
| `FoodSearchScreen` | `meal` 改可選；標題依 `meal` 分岔；送出前若 `meal` 未定則開選餐 sheet |
| `CreateMealController` | 允許在未指定 meal 的情況下開始一個 session，送出前才綁定 |
| l10n ARB ×3 | 字典標題、查詢入口的 tooltip、選餐 sheet 的標題 |

## UI/UX 設計

### 使用者路徑

**主路徑（純查詢）**：飲食頁 → 點 AppBar 的搜尋圖示 → 看到最愛清單 → 搜尋 → 每列顯示份量 → 看完返回。全程沒有任何記錄相關的 UI。

**查了之後決定要記**：同上 → 點一個食物 → tray 出現 → 可再加幾個 → 送出 → 選一餐 → 回到飲食頁看到結果。

**管理常用食物**：同入口 → 搜尋 → 點愛心加入/移除最愛。

**例外路徑**：
- 直接用網址開 `/health/diet/dictionary`（沒有 `extra`）→ redirect 回飲食頁（比照現有 food-search 的處理）。
- 未登入／401 → 沿用畫面既有的 reauth 呈現。
- 送出失敗 → 沿用既有錯誤處理，tray 保留。

### 介面與一致性

不新增畫面，字典就是既有的搜尋畫面在「還沒選餐」狀態下的樣子。AppBar 圖示用 `Icons.search`，與 app 內其他圖示一樣走主題色。選餐 bottom sheet 比照專案既有的 bottom sheet 慣例（行動裝置上帶文字輸入的對話框改用 bottom sheet 是這個 repo 的既有決定）。

### 狀態設計

- **剛進入**：搜尋欄 + 最愛清單。沒有 tray、沒有提交按鈕。
- **搜尋中**：結果列表（沿用既有的 loading／錯誤／空狀態）。
- **點了食物**：tray 從底部出現，提交按鈕跟著出現 —— 這是畫面上唯一「你正在記錄」的訊號。
- **送出**：選餐 sheet → 送出中 → 成功回飲食頁／失敗保留 tray 與錯誤。

### 可及性/理解性

查詢圖示要有 tooltip（螢幕閱讀器與長按都會用到）。選餐 sheet 的每個選項是標準 `ListTile`，可直接讀出餐別名稱。標題從「加入 {餐別}」變成「食物字典」是使用者能感知的差別 —— 它告訴你這次不是在記錄。

## 測試策略

- **screen（widget）**：`meal` 為 null 時標題是「食物字典」且**沒有**提交區；點食物後 tray 與提交區出現；送出時開選餐 sheet 並把選到的餐別傳給 controller；`meal` 已指定時行為與今天逐字相同（既有測試不得退化）。
- **入口（widget）**：飲食頁 AppBar 有查詢按鈕且帶 tooltip；點它會 push 到字典路由，並帶上**當下瀏覽的日期**（不是今天）與該日的 mealNames。
- **controller（單元）**：未指定 meal 的 session 可以加入 tray；送出前綁定 meal 後才呼叫 `CreateMeal`；未綁定就送出不會打後端。
- **路由**：`extra` 缺席時 redirect 回飲食頁（比照 food-search 既有測試）。
- **既有測試不得退化**：現有的 food-search 測試（從某一餐進入的完整流程）全部維持。

## 不做（YAGNI）

- 「更多」分頁再放一個入口 —— 同一個目的地兩個入口要維護，也可能讓人以為是兩個不同的東西。若之後發現飲食頁那個不夠被發現，再加。
- 每個食物各自選餐 —— 見 D3。
- 唯讀的字典畫面 —— 見 D2。
- 全域搜尋（app 層級）—— 超出 issue 範圍。
- 字典的分類／標籤瀏覽 —— issue 要的是「查詢」，搜尋 + 最愛已涵蓋。
